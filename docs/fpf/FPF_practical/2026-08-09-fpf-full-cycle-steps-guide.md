# Полный цикл FPF — пошаговое руководство (v2, сверено с семинарами 1–4)

> Правило: решения принимает пилот; агент применяет паттерны; один шаг — один файл — один следующий ход.
> Сверка 09.08: 4 семинара × 8 шагов цикла → GAP-ы закрыты этой версией.

## Главный ответ про E.9 (DRR)

**В цикле применения (шаги 0–10) отдельный проход по E.9 НЕ нужен.** Дословно из семинара 1 (LECTURE §2): «DRR — инструмент автора, а не часть FPF… для обычного применения FPF он не нужен».

**Семинар 5 подтвердил и дал точное место:** DRR — обязательный шаг 4 маршрута создания DPF (слой 2 ниже). Дословно (слайд 48): «AI-агент записывает в DRR точный вопрос, серьёзные альтернативы, выбранный человеком ответ, основания выбора, последствия, первый авторский ход и условие пересмотра. Решение принимает человек… По E.9.DA независимый проверяющий оценивает конкретную версию DRR… DRR нужен там, где без него следующий автор будет заново изобретать архитектурное решение. Для дешёвой обратимой правки он создаёт лишнюю работу».

**Граница простая:** применяешь метод к кейсу — слой 1, без DRR. Создаёшь/меняешь базу знаний (DPF/LPF/Pack) — слой 2, DRR на шаге 4. Шпаргалка: `2026-08-09-drr-workflow-guide.md`.

## Сквозные правила (действуют на КАЖДОМ шаге)

Из семинара 1 (раньше в цикле не были заявлены — GAP):

1. **Результат — в файл на диске** (md с frontmatter), не в чате.
2. **NextMove с ответственным и критерием готовности** в конце каждого файла; работа без следующего хода — «кисель».
3. **Границы шага:** когда остановиться / когда вернуться / что НЕ делать на этом проходе.
4. **Приёмка человеком:** пилот проверяет правдоподобность и принимает каждый шаг (в файле должно быть видно: на какой вопрос отвечает; что установлено, а что предположение; на чём держится вывод).
5. **Capture после шага** (E.18.1): что изменилось в рабочем ходе. Семинар ценен только изменением следующего хода.
6. **Ревьюер-контур для важных артефактов** (семинар 2): отдельный контекст + рубрика (что проверять) + решение человеком.

## Шаги цикла

### Шаг 0. Вход: зацепка и выбор карточки
- **Паттерны:** A.16.1 (сохранить раннюю зацепку без диагноза — cue pack) → E.11 (выбор README-карточки по problem frame).
- **Действие:** зафиксировать сигнал как есть; выбрать карточку-вход («какой паттерн управляет этой ситуацией»).
- **Форма:** cue pack (ядро зацепки, свидетель, 2–3 ветви; запрещены диагноз и маршрут) + название выбранной карточки.

### Шаг 1. Карточка проблемы (C.22.2)
- **Форма (5 полей):** EntityOfConcern, Constraints, Unresolved relations, Distinctions to preserve, **Acceptance basis с числовыми критериями** (пример из семинара 2: «обнаружение за 24 ч, ≤10 мин/день технолог»). Недостающие факты — вопросы пилоту, не додумывать.
- **Проверка связи с пользой** (семинар 3, системная мантра): довести «и что?» до пользы у клиента. Нет пользы — нет зачёта.

### Шаг 2. Граница системы (A.1, B.1.2, A.6.F)
- **Форма:** что входит/не входит; по каждому внешнему предмету — изменение состояния «от…к…» и кому это нужно; по внутренним частям — почему существенна.

### Шаг 3. Межуровневый конфликт (B.2)
- **Форма:** явный ответ «достаточно ли объяснения внутри системы»; таблица конфликтующих характеристик (локально разумное vs вред внешнему); финальный вопрос с ≥2 вариантами.

### Шаг 4. Выбор: метод и/или структура (мантра стратегирования + C.32)
- **Правила:** обязательно **>1 кандидата**; сравнение по характеристикам (A.19.ECS: шкалы, защищаемые компромиссы); выбор «наименее худшего» (C.11, ChoiceResult: условия, ограничения, что вернёт к пересмотру, что НЕ делать).
- **Если вопрос архитектурный** (как устроена система, а не какой метод): C.32.P2S (кандидаты структур) → **C.32.PAD — запись решения архитектора** (это «мини-DRR» внутри цикла, отдельный E.9 не нужен).
- **Форма:** ChoiceResult (+ PAD при архитектурном выборе). Недоминируемые кандидаты — в архив (C.18), не выбрасывать.

### Шаг 5. Method claim + описание метода (A.3.1, A.3.2)
- **Помнить три независимости:** метод ≠ описание ≠ запуск ≠ назначение (A.15).
- **Нормативные фразы — разбор LADE** (семинар 4, A.6.B): определения / допуск / обязанности / эффекты, каждое атомарно.
- **Форма method claim:** participant meanings, applicability, conditions, intended effect, bounds + honest stop (чего метод не обещает).

### Шаг 6. P2W-развёртка (карта 12 позиций)
- **Критерий изменения — отдельным артефактом** (позиция 2): «как узнаем, что проблема решена» — назвать заранее, с порогом. (GAP семинара 3: в v1 была форма без порога.)
- Карта — зависимость результатов, не календарный план. Место входа — первый неподтверждённый результат.

### Шаг 7. Потоки (E.18, A.12)
- Два потока: применения и создания/изменения («build the builder»). Таблица позиций «что происходит — тип (Transfer/Transformation/Work)». Не календарь.

### Шаг 8. Язык и публикация (семинар 4 — полный блок)
- **Проверка языка** (E.10/C.2.P): минимальный kind, предмет+утверждение восстановимы. «Выпускать в production результат без языковой чистки нельзя».
- **Два лица для двух читателей** (E.17): помощник vs руководство — два варианта описания, вердикт «одна эпистема или две».
- **Карточка огрубления** (A.6.3.CSC, 6 строк) для сводки руководителю — с возвратом к точности.
- **Именование** (F.18, NameCard): новые термины проекта — TechLabel/PlainLabel, отклонённые кандидаты с причинами, условие пересмотра.
- **Нарративизация** (A.6.3.NAR) — если нужен рассказ по материалам: приёмка NSTD.7 (владелец допуска) → NSTD.6 (6 критериев).

### Шаг 9. Пилот и измерение (хвост цикла — в v1 отсутствовал!)
- **Телеметрия обязательна** (семинар 3): измерительная система + значения **до/после**. «Архитектура без ожиданий — идиотизм».
- Замер базовой линии → старт пилота метода → измерение → сравнение с критерием из шага 6.

### Шаг 10. Приёмка и решение
- **Вопрос-приёмка:** «в проекте что-нибудь изменилось? какой следующий ход?» (семинар 3). Работа принимается, когда целевая система работает у клиента.
- **Решение о проблеме** (позиция 12): подтверждена / нет → красная ветка: диагностировать метод / выполнение / причинную гипотезу.
- **Гроссбух:** «занеси, что чинили и как» — регрессионный журнал проверок (семинар 3).

## Куда вшит DRR-контур (без отдельного прохода)

| Место цикла | DRR-функция |
|---|---|
| Шаг 4, C.32.PAD | Запись решения архитектора (мини-DRR внутри цикла) |
| Шаг 8, карточка точности | Запись решения о формулировке (заводится, когда решение передаётся/может быть оспорено) |
| После цикла: метод → LPF | Полный E.9 → E.9.DA → E.23 → принятие (см. drr-workflow-guide) |

## Слой 2: создание своего DPF/LPF (семинар 5, 09.08)

> Цикл выше (шаги 0–10) — **применение**: метод существует. Семинар 5 добавляет слой **создания**: метода нет, и ты становишься автором. Мостик между слоями — гейт нужности.

### Гейт нужности фреймворка (прежде чем писать DPF)

Первичный дефицит (практика 1): что не хватает — FPF / DPF / LPF / предметного результата / фреймворк не нужен. Дешёвые выходы проверяются ДО авторства: применить готовый FPF/DPF; тонкий маршрут к источникам; один разовый ответ; честная остановка. «Для дешёвой обратимой правки DRR создаёт лишнюю работу» (слайд 48).

### Различение DPF vs LPF (слайды 4, 11–13)

- **DPF** — переносимое знание о повторяющихся ситуациях и способах работы (область: тепличные огурцы, молочное скотоводство). Не словарь, не обзор литературы.
- **LPF** — воспроизводимая местная практика подготовки, применения, проверки и обновления этого знания (одна организация/команда/роль). «Более узкий контекст не превращает его в список инструкций».
- **Критерий переноса:** применяется ко всему классу → кандидат в DPF; нужен для регулярной работы именно этого предприятия → кандидат в LPF.
- Привязка к нашей работе: метод B, описания D1–D4, чек-листы ролей — кандидаты в **LPF отдела** (местная практика), не в DPF отрасли.

### Маршрут создания (12 шагов, рабочая поверхность семинара)

1. **Трудность / нужный результат** — как в шаге 1 цикла применения
2. **Три различающихся случая + общий вопрос** (+ near-miss контрпример) — корпус случаев, не одна ситуация
3. **SoTA по G.2** — ≥3 различающиеся линии источников, synthesis account, без преждевременного слияния
4. **Intake / кандидаты / DRR / E.9.DA** — архитектурное решение о границе фреймворка: человек выбирает, агент записывает в DRR (вопрос, альтернативы, выбранный ответ, основания, последствия, первый ход, условие пересмотра), независимый проверяющий — по E.9.DA **до переноса** (landing), не «вечный статус»
5. **Первый паттерн и Solution** — узнаваемое начало; приёмка холодным читателем
6. **Функции тела паттерна** — каркас E.8 (12 разделов + `### <PatternId>:End`); «все заголовки ≠ зрелый паттерн»
7. **Пакет** — README/Preface/ToC/Pattern Index + полные тела + карта источников + Refresh Route (G.11)
8. **Применение к новому случаю** — не использованному при авторстве
9. **Местный LPF** — роли, инструменты, данные, ограничения безопасности, способ проверки, условия остановки, 3–5 несводимых характеристик с нижними границами; форма та же FPF-подобная
10. **Оценка / ремонт / повтор** — цикл E.23 до проверенного изменения предмета
11. **Контур / узкое место / агенты** — контурная инженерия, закон Амдала, обоснование числа агентов
12. **А. Мини-DPF принятой редакции** (приёмка по E.4.DPF.DA) / **Б. Местный цикл** — изменение конкретного предмета, воспроизводимость другим исполнителем

### Три объекта оценки — не смешивать (слайды 41, 101)

| Объект | Рубрика |
|---|---|
| Тело паттерна | E.21 |
| Пакет DPF/LPF | E.4.DPF.DA |
| DRR | E.9.DA |
| Предметный результат | характеристики своей области (A.19.ECS) |

Шкала 0–5: **4 — рабочая нижняя граница пригодности (floor)**; 5 — не обязательная цель. «Один общий средний балл скрыл бы эти различия». Прежний PASS не переносится на изменённый master автоматически — после ремонта повторная оценка затронутых координат.

### Приёмка мини-DPF/LPF (слайд 137) — все пункты обязательны

Предметное изменение + перенос на новый неидентичный случай + повторяемость другим исполнителем + защищаемые характеристики + пакет проверен по E.4.DPF.DA. «Если один пункт не закрыт, результат остаётся кандидатом».

### Ветвления возврата из finding (слайды 52, 86)

Местные условия → в LPF · слаб способ → в паттерн · не держится архитектура → в DRR · пропущена сильная линия → в SoTA · неверна исходная трудность → в intake.

## Карта статусов (обновлённая)

Каждый файл шага: `⏳ не начат / 🔄 в работе / ◐ на приёмке пилота / ✅ принят`. Переход ◐→✅ — только решением пилота (стадия «принятие» из DRR-цикла: записано ≠ принято).
