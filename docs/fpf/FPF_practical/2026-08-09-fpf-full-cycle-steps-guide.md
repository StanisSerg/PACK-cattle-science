# Полный цикл FPF — пошаговое руководство (v2.1, сверено с семинарами 1–5)

> Правило: решения принимает пилот; агент применяет паттерны; один шаг — один файл — один следующий ход.
> Сверка 09.08: 4 семинара × 8 шагов цикла → GAP-ы закрыты этой версией.
> Сверка 23.08 (семинары 1–5, отчёт `2026-08-23-route-verification-seminars-1-5.md`) → точечные правки: шаг 7 перестроен (три структуры, таблица 5 групп полей), шаг 6 — 8-ходовая форма P2W, шаг 1 — поля C.22.PFR, сквозное правило 5 исправлено (E.18.1 — carry-through, не capture).

## Главный ответ про E.9 (DRR)

**В цикле применения (шаги 0–10) отдельный проход по E.9 НЕ нужен.** Дословно из семинара 1 (LECTURE §2): «DRR — инструмент автора, а не часть FPF… для обычного применения FPF он не нужен». *(Атрибуция уточнена по сверке 23.08: в слайдах сем.1 этой фразы нет — вероятно, источником является конспект лекции; точный источник цитаты требует уточнения.)*

**Семинар 5 подтвердил и дал точное место:** DRR — обязательный шаг 4 маршрута создания DPF (слой 2 ниже). Дословно (слайд 48): «AI-агент записывает в DRR точный вопрос, серьёзные альтернативы, выбранный человеком ответ, основания выбора, последствия, первый авторский ход и условие пересмотра. Решение принимает человек… По E.9.DA независимый проверяющий оценивает конкретную версию DRR… DRR нужен там, где без него следующий автор будет заново изобретать архитектурное решение. Для дешёвой обратимой правки он создаёт лишнюю работу».

**Граница простая:** применяешь метод к кейсу — слой 1, без DRR. Создаёшь/меняешь базу знаний (DPF/LPF/Pack) — слой 2, DRR на шаге 4. Шпаргалка: `2026-08-09-drr-workflow-guide.md`.

## Сквозные правила (действуют на КАЖДОМ шаге)

Из семинара 1 (раньше в цикле не были заявлены — GAP):

1. **Результат — в файл на диске** (md с frontmatter), не в чате.
2. **NextMove с ответственным и критерием готовности** в конце каждого файла; работа без следующего хода — «кисель».
3. **Границы шага:** когда остановиться / когда вернуться / что НЕ делать на этом проходе.
4. **Приёмка человеком:** пилот проверяет правдоподобность и принимает каждый шаг (в файле должно быть видно: на какой вопрос отвечает; что установлено, а что предположение; на чём держится вывод).
5. **Carry-through одного принятого различия** (E.18.1) *(исправлено по сверке 23.08: ранее ошибочно описано как «capture после шага»; функция capture в сем.3 подтверждается, но E.18.1 — не о ней)*: микромантра локальной P2W «удержать–спросить–применить–продолжить–вернуться» (сем.3 сл.129) — пронести одно принятое различие через один переход длинной мантры, не меняя kind результата ради рассказа; при изменении опоры пересмотреть только зависящий фрагмент. Семинар ценен только изменением следующего хода.
6. **Ревьюер-контур для важных артефактов** (семинар 2): отдельный контекст + рубрика (что проверять) + решение человеком.

## Шаги цикла

### Шаг 0. Вход: зацепка и выбор карточки
- **Паттерны:** A.16.1 (сохранить раннюю зацепку без диагноза — cue pack) → E.11 (выбор README-карточки по problem frame).
- **Действие:** зафиксировать сигнал как есть; выбрать карточку-вход («какой паттерн управляет этой ситуацией»).
- **Форма:** cue pack — **5 элементов** (сем.4 сл.53; ранее в гайде — 3, дополнено по сверке 23.08): значимое ядро (cue nucleus); **почему его стоит не потерять**; главный свидетель/опора со ссылкой на исходный сигнал; **контрасты/примеры, делающие зацепку узнаваемой**; ранние намёки на 2–3 направления разбора (не выбранный маршрут). Запрещены диагноз и маршрут. + название выбранной карточки.
- **Уточнение обратимо** (A.16.2, сем.4 сл.55): исходный материал и путь возврата сохраняют; reopen — возврат альтернатив в той же семье, sketchBackoff — снятие преждевременной определённости назад к пакету зацепки.
- **Из ряда продолжений — один предмет** (сем.3 сл.29): для одной гипотезы о полезном продолжении выбирают один предмет (cue pack / RoutedCueSet / абдуктивная постановка / карточка проблемы / сигнатура задачи), а не проходят весь ряд; каждый сохраняет собственный kind.

### Шаг 1. Карточка проблемы (C.22.2)
- **Форма (5 полей спеки + 2 поля семинарской формы):** EntityOfConcern, Constraints, Unresolved relations, Distinctions to preserve, **Acceptance basis с числовыми критериями** (пример: «обнаружение за 24 ч, ≤10 мин/день технолог» — *источник примера требует уточнения: в слайдах сем.1–5 не находится, атрибуция семинару 2 снята по сверке 23.08*). Дополнительно из семинарной формы (дополнено по сверке 23.08): **работа, в которой предполагается использовать ответ / какую работу затрудняет проблема, включая работу выбора** (сем.1 сл.51; сем.3 сл.28, C.22.PFR) и **область пригодности: для каких ситуаций и на каком интервале утверждение пригодно** (сем.3 сл.28). Недостающие факты — вопросы пилоту, не додумывать.
- **Проверка «прогноз/риск ≠ фактическая проблема»** (сем.3 сл.28): предполагаемая опасность или возможная будущая проблема — модальное утверждение в карточке, его не выдают за уже имеющее место положение дел.
- **Проверка связи с пользой** (семинар 3, системная мантра): довести «и что?» до пользы у клиента. Нет пользы — нет зачёта.

### Шаг 2. Граница системы (A.1, B.1.2, A.6.F)
- **Форма:** что входит/не входит; по каждому внешнему предмету — изменение состояния «от…к…» и кому это нужно; по внутренним частям — почему существенна.
- **Граница — рабочая гипотеза до проверки** (сем.2 сл.10): рабочей она становится только вместе с правилом тождества выбранной системы и проверенными утверждениями о фактических отношениях частей и окружения. Смена границы — отдельное решение с явными условиями включения, исключения и сохранения тождества (там же).
- **Пересечение ≠ ComponentOf** (сем.2 сл.10, 74): ни пересечение границы (энергия, вещество, сигнал, документ), ни взаимодействие через неё сами по себе не устанавливают отношение части к целому.

### Шаг 3. Межуровневый конфликт (B.2)
- **Форма:** явный ответ «достаточно ли объяснения внутри системы»; таблица конфликтующих характеристик (локально разумное vs вред внешнему); финальный вопрос с ≥2 вариантами.
- **Сначала ExistingWholeExplanationCheck** (сем.2 сл.26): проверить все объяснения с прежним холоном (части/отношения, измерения, интервал/фаза, описание метода и работы, архитектурный вид); если хотя бы одно достаточно — B.2 не открывать. Смена уровня рассмотрения между уже существующими холонами ≠ метасистемный переход (там же).
- **Не предполагать конфликт заранее; «неизвестно» — легальный исход** при нехватке фактов (сем.2 сл.30). Для постановки конфликта нужна «общая структура»: названы области обоих холонов и структура/вид структуры, несущие обе области (сем.2 сл.27).

### Шаг 4. Выбор: метод и/или структура (мантра стратегирования + C.32)
- **Правила:** обязательно **>1 кандидата** — палитра **2–5 различающихся кандидатов** (сем.2 сл.96, 134); сравнение по характеристикам (A.19.ECS: шкалы, защищаемые компромиссы); выбор «наименее худшего» (C.11, ChoiceResult: условия, ограничения, что вернёт к пересмотру, что НЕ делать).
- **Строка кандидата в палитре** (сем.2 сл.134): изменения структур, затронутые характеристики, ожидаемый выигрыш, известная потеря, соответствие ограничениям, сохраняемые/теряемые отношения, условие возврата к источнику, следующая работа.
- **«Принудительно выбирать не надо»** (сем.2 сл.94): если ни один кандидат не даёт выигрыша без неприемлемой потери — возврат к исходной задаче, границе, составу структур или критериям. **4 исхода C.11** (сем.2 сл.138): выбрать сейчас / отвергнуть текущий набор / провести ещё одну пробу / сменить направление.
- **TaskSignature@Context между карточкой проблемы и кандидатами** (сем.3 сл.30): короткая запись различий, по которым сравнивают методы; **«неизвестное сохраняют неизвестным, не нулём»** — с указанием, какое решение от него зависит.
- **Ветвь «различающая проба вместо выбора»** (сем.3 сл.34, 36): иногда дешевле сначала проверить предположение, от которого зависит выбор (абдуктивная мантра B.5.2: конкурирующие объяснения → различающее следствие → малая проба → пересмотр). «Честная исследовательская работа» — легитимный итог стратегирования (сем.3 сл.36).
- **Если вопрос архитектурный** (как устроена система, а не какой метод): C.32.P2S (кандидаты структур) → **C.32.PAD — запись решения архитектора** (это «мини-DRR» внутри цикла, отдельный E.9 не нужен). Состав PAD (сем.2 сл.139): холон, выбранный вариант, затронутые структуры, принятые потери, ограничения, которые нельзя нарушать, и изменения-триггеры пересмотра. **Условия пересмотра — явные** (сем.2 сл.115): выход подтверждённого значения за защитную границу, смена принятого уровня потери, существенная смена базы кандидатов, устаревший источник; «новый вариант или сигнал панели сам по себе — не повод».
- **Форма:** ChoiceResult (+ PAD при архитектурном выборе). Недоминируемые кандидаты — в архив (C.18), не выбрасывать.

### Шаг 5. Method claim + описание метода (A.3.1, A.3.2)
- **Помнить три независимости:** метод ≠ описание ≠ запуск ≠ назначение (A.15).
- **Критерий U.Method** (сем.2 сл.44): способ действия признают методом, когда описано — для кого и чего предназначен, когда применим, при каких условиях, что должен дать или сохранить и **где заканчивается** (граница завершения метода).
- **Новая редакция описания ≠ новый метод** (сем.2 сл.66): изменение самого метода проверяют отдельно по A.3.1; связь редакций описания устанавливают отдельно.
- **Механизм ≠ метод** (A.6.1, сем.3 сл.38): механизм объявляет закон операции (аргументы, выход, условия допустимости); метод — воспроизводимый способ получить преобразование, он может использовать операции механизма, но не сводится к ним.
- **Приспособление метода — отдельный подшаг** (сем.3 сл.42): уточняют параметры и условия применимости. **Ресурсы, исполнители и время — не части метода**, они остаются содержанием плана и состоявшейся работы. Итог приспособления — новая версия метода + редакция описания, это ещё не U.WorkPlan.
- **Составной метод** (сем.3 сл.41): собирают только из подметодов, уже определённых как U.Method, с названными отношениями между ними; **если выход одного подметода не подходит на вход другого напрямую — указывают преобразующий адаптер** (сходство слов «выход»/«вход» совместимость не устанавливает).
- **Нормативные фразы — разбор LADE** (семинар 4, A.6.B): определения / допуск / обязанности / эффекты, каждое атомарно.
- **Форма method claim:** participant meanings, applicability, conditions, intended effect, bounds + honest stop (чего метод не обещает).

### Шаг 6. P2W-развёртка (большая мантра, 8 ходов — сем.3 сл.10–11)
*(Перестроено по сверке 23.08: ранее «карта 12 позиций» — число 12 в слайдах семинаров не находится; первоисточник описывает ровно 8 ходов.)*
- **8 ходов, у каждого «Результат» + «Следующая работа»:** (1) поставить проблему и способ проверки решения → карточка + основание проверки; (2) стратегировать → сопоставимые кандидаты либо честно названная исследовательская задача; (3) прикинуть выполнимость при данных ресурсах; (4) выбрать и приспособить метод; (5) наметить работы и установить готовность одной из них (U.WorkPlan + WorkEntryReadiness@Context); (6) выполнить работу (сам факт выполнения ≠ нужное изменение); (7) установить, что изменилось (измеренные значения); (8) оценить и выбрать продолжение.
- **Критерий изменения — отдельным артефактом** (внутри хода 1): «как узнаем, что проблема решена» — назвать заранее, с порогом.
- **Обратный проход — 5 уровней проверки от позднего сбоя** (сем.3 сл.12): что действительно изменилось и как измерено → какая работа фактически состоялась и следовала ли методу → готовность, план, ресурсы → приспособление и выбор метода → критерий и постановка проблемы. Ищут **самый ранний неверный результат, на который опирались поздние решения**.
- **Возврат — только к названному узлу карты** (сем.3 сл.11): произвольный новый ход запрещён. Карта — зависимость результатов, не календарный план.

### Шаг 7. Потоки (E.18, A.12)
*(Перестроено по сверке 23.08: было «два потока» и смешанная колонка «тип».)*
- **Три структуры, не две** (сем.2 сл.61): применение системы / её выпуск или изменение / изменение исполнителя (build-the-builder — третья структура; ход «сначала изменить исполнителя» требует точных межпотоковых отношений и привязок к позициям, общее имя структуры не соединяет).
- **Структура потока** (сем.3 сл.88): позиции преобразований и соседних значений + **один типизированный вид отношения — U.Transfer** + ограничения. Transfer/Transformation/Work — это kinds значений в позициях, а не варианты одной колонки «тип». Позиция связывает значение со структурой, **не меняя его kind** (сл.90): позиция механизма связывает механизм, а не работу по его применению.
- **U.Transfer не утверждает причинность, временное предшествование или готовность следующей работы** (сл.91) — каждый такой вывод устанавливают по своему отношению.
- **Таблица потока — 5 групп полей на строку** (сем.3 сл.145): (1) имя позиции и для чего она нужна; (2) допустимый kind значения и профильный паттерн; (3) ссылка на конкретное значение и правило привязки; (4) отношения U.Transfer и существенные ограничения продолжения; (5) путь/срез/оценивание потока, если выбор зависит от них. Метод, план, работу и преобразование не помещают в одну безымянную позицию.
- **Запрет «безымянных стрелок»** (сл.89): смысл перехода задают подписанное отношение и его условия, а не расположение строк.
- **Допустимый путь ≠ одобренный или пройденный** (сл.92): выбор выполняют отдельно и сохраняют в ChoiceResult. **Цикл ≠ улучшение** (сл.93): надо назвать улучшаемый предмет, критерии и отношения между версиями.
- **Сквозной запрет:** связь работа↔преобразование — только прямым отношением; соседства во времени или в рассказе недостаточно (сем.3 сл.11).

### Шаг 8. Язык и публикация (семинар 4 — полный блок)
- **Правило входа** (сем.2 сл.45; сем.4 сл.68/74): фрагмент намеренно использует FPF-термины/идентификаторы или заявляет соответствие FPF → **E.10**; обычное исходное выражение → **C.2.P** (тесты E.10 можно заимствовать). Одного слова «роль»/«процесс»/«готов» недостаточно; признак — повод спросить, а не запретить слово; если читатель и так однозначно восстанавливает смысл и различение не влияет на работу — локальную формулировку не трогают.
- **Мантра распаковки — 5 ходов** (сем.2 сл.52): начните с решения → назовите утверждение и предмет → назовите действующую систему и работу → разведите предмет и описание → вернитесь к решению.
- **Проверка языка** (E.10/C.2.P): минимальный kind, предмет+утверждение восстановимы. «Выпускать в production результат без языковой чистки нельзя».
- **Публикация — 5 участников** (E.24.PUB, сем.4 сл.33): редакция эпистемы, описание аудитории, заявление о пределах использования, публикационная форма, носитель. **Пределы публикации** — для какой работы годится и какой более сильный вывод пока не обоснован. **Доступность ≠ прочитано** (сем.2 сл.152): публикация не доказывает, что участник прочитал, положился на текст или выполнил по нему работу.
- **Мантра публикации — 6 пунктов** (сем.4 сл.40): редакция → читатель и его работа → форма и язык → носитель и доступ → пределы → **возврат** (куда вернуться за большей точностью).
- **Два лица для двух читателей** (E.17): помощник vs руководство — два варианта описания, вердикт «одна эпистема или две».
- **F.19 — обычная фраза после восстановления** (сем.4 сл.109): отделить предметное содержание от служебного аппарата → восстановить точность → написать кратчайшую обычную техническую фразу с тем же смыслом → проверить на предполагаемом читателе; если исчезли граница применимости, модальность, исполнитель — вернуть их понятными словами.
- **Карточка огрубления** (A.6.3.CSC, 6 строк) для сводки руководителю — с возвратом к точности.
- **Именование** (F.18, NameCard): новые термины проекта — TechLabel/PlainLabel, отклонённые кандидаты с причинами, условие пересмотра.
- **Нарративизация** (A.6.3.NAR) — если нужен рассказ по материалам: приёмка NSTD.7 (владелец допуска) → NSTD.6 (6 критериев).

### Шаг 9. Пилот и измерение (хвост цикла — в v1 отсутствовал!)
- **Гейт готовности перед стартом** (сем.3 сл.48, 140): WorkEntryReadiness@Context для одной намеченной работы + FullKit (всё, что должно быть готово к границе начала: сведения, предмет, инструмент, договорённости; состав — с учётом метода и цены прерывания). **4 ветви при неготовности:** подготовить недостающее / назначить другого исполнителя / выбрать иной метод / создать или изменить систему-преобразователь.
- **Режим «сначала менее дорогой и более обратимый опыт»** (сем.1 сл.69): для дорогой или трудно обратимой работы — сравнить режимы (выполнить сейчас / сначала небольшой опыт / сузить предположение / получить недостающие сведения), выбор фиксируют в ChoiceResult.
- **Установление преобразования — 4 пункта** (сем.3 сл.50): изменившийся предмет; граница (интервал), через которую произошло изменение; условия отнесения к этому случаю; факты до/во время/после (+ правило отнесения наблюдений к одному преобразованию при разрыве). По описанию метода, плану или модели установить преобразование нельзя.
- **Выполнение работы ≠ нужное изменение** (сем.3 сл.11, 51): сам факт выполнения не доказывает преобразования.
- **Наблюдение может изменить систему** (сем.2 сл.112): опрос, публикация рейтинга или прогноза могут сами воздействовать на наблюдаемую систему — это отдельное причинное утверждение; эпистема ≠ фактическое состояние системы.
- **Телеметрия обязательна** (семинар 3): измерительная система + значения **до/после**. «Архитектура без ожиданий — идиотизм».
- Замер базовой линии → старт пилота метода → измерение → сравнение с критерием из шага 6.

### Шаг 10. Приёмка и решение
- **5 исходов E.23 вместо бинарного** (сем.2 сл.66): остановиться / продолжить / сменить способ улучшения / поставить новую задачу (openNewFrame) / ждать достаточных сведений (точно назвать недостающие сведения и условие достаточности). Продолжают только ради заранее названного изменения на шкале оценки, оправдывающего стоимость и риск.
- **Диагностика неудачи — 5 конкурирующих объяснений** (сем.3 сл.51): метод не подходил к условиям / не хватило способности исполнителя / работа выполнена не по методу / работа меняла другой предмет / неверна постановка ожидаемого изменения. Вопрос не «кто виноват?», а «к какому узлу карты вернуться?» (см. шаг 6, обратный проход).
- **Проверка Гудхарта** (E.13, сем.2 сл.90): не подменил ли показатель цель — удобное измерение или балл стало самостоятельной целью/порогом, показатель движется в нужную сторону, а практический результат — нет.
- **E.11.PUA** (сем.3 сл.60): «можно как-нибудь использовать» недостаточно — результат полезен, когда удовлетворяет условию конкретной работы или ветви выбранной мантры.
- **Вопрос-приёмка:** «в проекте что-нибудь изменилось? какой следующий ход?» (семинар 3). Работа принимается, когда целевая система работает у клиента.
- **Гроссбух:** «занеси, что чинили и как» — регрессионный журнал проверок (семинар 3).

## Слой 2: создание своего DPF/LPF (семинар 5, 09.08)

> Цикл выше (шаги 0–10) — **применение**: метод существует. Семинар 5 добавляет слой **создания**: метода нет, и ты становишься автором. Мостик между слоями — гейт нужности.

### Гейт нужности фреймворка (прежде чем писать DPF)

Первичный дефицит (практика 1): что не хватает — FPF / DPF / LPF / предметного результата / фреймворк не нужен. Дешёвые выходы проверяются ДО авторства: применить готовый FPF/DPF; тонкий маршрут к источникам; один разовый ответ; честная остановка. «Для дешёвой обратимой правки DRR создаёт лишнюю работу» (слайд 48).

### Различение DPF vs LPF (слайды 4, 11–13)

- **DPF** — переносимое знание о повторяющихся ситуациях и способах работы (область: тепличные огурцы, молочное скотоводство). Не словарь, не обзор литературы.
- **LPF** — воспроизводимая местная практика подготовки, применения, проверки и обновления этого знания (одна организация/команда/роль). «Более узкий контекст не превращает его в список инструкций».
- **Критерий переноса:** применяется ко всему классу → кандидат в DPF; нужен для регулярной работы именно этого предприятия → кандидат в LPF.
- Привязка к нашей работе: метод B, описания D1–D4, чек-листы ролей — кандидаты в **LPF отдела** (местная практика), не в DPF отрасли.

### Маршрут создания (12 шагов, рабочая поверхность семинара)

1. **Трудность / нужный результат** — как в шаге 1 цикла применения
2. **Три различающихся случая + общий вопрос** (+ near-miss контрпример) — корпус случаев, не одна ситуация
3. **SoTA по G.2** — ≥3 различающиеся линии источников, synthesis account, без преждевременного слияния
4. **Intake / кандидаты / DRR / E.9.DA** — архитектурное решение о границе фреймворка: человек выбирает, агент записывает в DRR (вопрос, альтернативы, выбранный ответ, основания, последствия, первый ход, условие пересмотра), независимый проверяющий — по E.9.DA **до переноса** (landing), не «вечный статус»
5. **Первый паттерн и Solution** — узнаваемое начало; приёмка холодным читателем
6. **Функции тела паттерна** — каркас E.8 (12 разделов + `### <PatternId>:End`); «все заголовки ≠ зрелый паттерн»
7. **Пакет** — README/Preface/ToC/Pattern Index + полные тела + карта источников + Refresh Route (G.11)
8. **Применение к новому случаю** — не использованному при авторстве
9. **Местный LPF** — роли, инструменты, данные, ограничения безопасности, способ проверки, условия остановки, 3–5 несводимых характеристик с нижними границами; форма та же FPF-подобная
10. **Оценка / ремонт / повтор** — цикл E.23 до проверенного изменения предмета
11. **Контур / узкое место / агенты** — контурная инженерия, закон Амдала, обоснование числа агентов
12. **А. Мини-DPF принятой редакции** (приёмка по E.4.DPF.DA) / **Б. Местный цикл** — изменение конкретного предмета, воспроизводимость другим исполнителем

### Три объекта оценки — не смешивать (слайды 41, 101)

| Объект | Рубрика |
|---|---|
| Тело паттерна | E.21 |
| Пакет DPF/LPF | E.4.DPF.DA |
| DRR | E.9.DA |
| Предметный результат | характеристики своей области (A.19.ECS) |

Шкала 0–5: **4 — рабочая нижняя граница пригодности (floor)**; 5 — не обязательная цель. «Один общий средний балл скрыл бы эти различия». Прежний PASS не переносится на изменённый master автоматически — после ремонта повторная оценка затронутых координат.

### Приёмка мини-DPF/LPF (слайд 137) — все пункты обязательны

Предметное изменение + перенос на новый неидентичный случай + повторяемость другим исполнителем + защищаемые характеристики + пакет проверен по E.4.DPF.DA. «Если один пункт не закрыт, результат остаётся кандидатом».

### Ветвления возврата из finding (слайды 52, 86)

Местные условия → в LPF · слаб способ → в паттерн · не держится архитектура → в DRR · пропущена сильная линия → в SoTA · неверна исходная трудность → в intake.
