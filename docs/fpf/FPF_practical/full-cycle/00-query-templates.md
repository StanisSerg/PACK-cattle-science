# Запросы к FPF-агенту по шагам цикла

> Как пользоваться: скопировать шаблон, подставить своё в `[скобках]`, приложить FPF файлом (не вставкой в промпт), ответ просить в отдельный md-файл.
> Общие правила (семинар 1): сильная модель; один запрос — один шаг; не «сделай весь проект»; ответ проверять по диагонали — ищем следующий ход.

## Анатомия запроса (как строятся запросы семинаров 3–4)

Запрос — это **микро-P2W**: шесть элементов в фиксированном порядке.

1. **Контекст с адресом разрыва.** Не «у меня проект», а «в проекте X есть разорванный переход N→N+1 развёртки: [суть]». Агент получает уже названный переход, а не ищет его сам.
2. **«Найди и примени [код] (полное имя паттерна)».** Явный адрес + полное имя: `A.3.1 (U.Method)`, `A.6.3.CSC (Controlled Semantic Coarsening)`. В обычной работе паттерн может искать сам агент; при обучении и спорных местах — называть явно.
3. **Шаги «сначала… затем…»** — порядок применения: сначала восстановить предмет, затем проверку, затем формулировку.
4. **Ограничители честности:** «не выдумывай факты проекта; где не хватает сведений — явный пробел», «не ставь диагноз», «не исправляй весь документ», «не выдавай выбор паттерна за выбор предметного метода».
5. **Формат результата:** именованные поля («method claim с полями…», «шесть строк карточки») + «пиши ответ в файл».
6. **Проверка по диагонали** — в шаблоне после каждого запроса: критерий брака и что делать, если агент угадывает («начинай с двух вопросов: о чём? и что утверждается?»).

## MCP-рецепт: три инструмента по ситуации (capture семинара 3)

| Ситуация                                 | Инструмент | Как                                                                                                                                  |
| ------------------------------------------------ | -------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| Адрес паттерна неизвестен | `search_fpf`       | 2–4 ключевых слова = предмет + действие                                                                    |
| ID известен                              | `read_fpf_doc`     | сначала`preview`, потом `full` с лимитом 6–9K знаков (страницы целиком не читать) |
| Нужен прикладной ответ       | `query_fpf_spec`   | режимы compact / verbose / proof (для обязательств — proof)                                                       |

Две формулы вопроса, которые срабатывают:

- **Найти адрес:** «Какой паттерн управляет `<предмет/отношение>`?»
- **Вытащить Solution:** «Что обязано содержать `<X>` по `<паттерн>`? Дай точные обязательства / чек-лист».

Правила точности: имена паттернов в вопросе (E.18, A.3.1) заметно повышают качество; вопрос по-русски, термины-ключи английскими (`method`, `transfer`, `mantra`, `work plan`); подстановку «яблок из жизни» делает человек — корпус даёт только обязательства. Цикл: затруднение → search/query → паттерн → Solution → применение к своему случаю → результат или честная остановка.

## Шаг 01 — Карточка проблемы (C.22.2)

**Шаблон:**

```
Вот сигнал из моего проекта: [что наблюдаю — 2-3 предложения, факты без оценок].
Контекст: [где и когда это происходит, кто участвует].
Следующая работа: подобрать и сравнить методы-кандидаты.
Найди и примени C.22.2 (ProblemCard@Context): собери карточку проблемы —
наблюдаемый сигнал, bounded context, граница принятой проблемы,
признак существенного улучшения, следующее использование карточки.
Не выдумывай факты; каких сведений не хватает — назови явным пробелом.
Пиши ответ в файл.
```

**Пример (B-01):**

```
Сигнал: сводки по молоку с фермы приходят каждые 2 дня, но между отклонением
и моим ответом технологу проходит 2-5 дней; часть сводок остаётся без ответа.
Контекст: хозяйство в РБ, 1 ведущий технолог (я), 2 помощника, учёт в АМТС.
Следующая работа: подобрать и сравнить методы-кандидаты.
Найди и примени C.22.2: собери карточку проблемы. Не выдумывай факты;
чего не хватает — явный пробел. Пиши ответ в файл.
```

**Проверка ответа:** в карточке видно, по какому признаку мы поймём, что стало лучше. Если признак = «отчёты обрабатываются» — плохо (это активность); если «время от отклонения до решения ≤ 1 дня» — хорошо (изменение).

## Шаг 02 — Граница системы (B.1.2, A.1, A.6.F)

**Шаблон:**

```
Проблема: [карточка из шага 01 или 2-3 предложения].
Найди и примени B.1.2 (System Aggregation and Holon Delimitation) и A.1
(Holon Ontic Foundation):
1. Назови физическую систему (не модель, не документ, не имя).
2. Что входит в границу, что снаружи.
3. Назови 2-3 внешних предмета: что система должна менять в их состоянии
   «от … к …» и кому/чему это нужно в окружении (A.6.F Function).
4. Посмотри внутрь: 2 части/отношения, существенные для проблемы.
Сначала наружу и вверх, потом внутрь. Пиши ответ в файл.
```

**Проверка ответа:** если «система» оказалась документом или программой без физики — ответ бракуем: граница проведена вокруг описания, а не холона.

## Шаг 03 — Межуровневый конфликт (B.2)

**Шаблон:**

```
Система и её окружение: [из шага 02].
Симптом: [что не сходится].
Найди и примени B.2 (Meta-Holon Transition): есть ли межуровневый конфликт —
локально разумное изменение внутри системы, которое вредит внешнему участнику
или целому? Назови обе стороны конфликта (что выигрывает один уровень,
что теряет другой). Если конфликта нет — скажи прямо, не придумывай.
Пиши ответ в файл.
```

**Пример (B-01):** «Полнота и частота данных для системы анализа ↔ время технолога (≤10 мин/день); детальные оповещения ↔ внимание пилота (≤15 мин/день)».

**Проверка ответа:** конфликт сформулирован как пара «X уровня N ↔ Y уровня N+1», а не как «всё сложно».

## Шаг 04 — Стратегирование метода (A.19.ECS, C.11)

**Шаблон:**

```
Принятая проблема: [карточка из шага 01].
Ограничения и конфликты: [из шага 03].
Следующая работа: выбрать метод.
Действуй по мантре стратегирования:
1. Сформулируй сигнатуру искомого метода (предмет, конечное состояние,
   название операции).
2. Предложи НЕ МЕНЕЕ ТРЁХ методов-кандидатов разного типа
   (обучение людей / автоматизация / изменение процесса).
3. Найди и примени A.19.ECS (Evaluation CharacteristicSpace Construction):
   задай характеристики сравнения и шкалы (мои ограничения — как критерии).
4. Сравни кандидатов, назови недоминируемых.
5. Рекомендуй «наименее худший» (C.11 Choice) с инженерным обоснованием —
   явно укажи, при каких условиях выбор неверен.
Не выдумывай факты; непроработанные кандидаты помечай. Пиши ответ в файл.
```

**Проверка ответа:** один кандидат = брак («единственный вариант» — признак, что агент продаёт, а не сравнивает). Обоснование должно содержать условие опровержения.

## Шаг 05 — Method claim + описание (A.3.1, A.3.2)

**Шаблон (форма семинара 3, проверена на проходе 4→5):**

```
В моём проекте [название] есть разорванный переход [N→N+1] развёртки:
метод [название] существует только как моя ручная практика и не оформлен
как передаваемый способ, который могут выполнять [исполнители].

Используя FPF:
1. Открой A.3.1 (U.Method) и A.3.2 (U.MethodDescription) и дай точные
   обязательства (Solution) обоих паттернов: что обязано содержать
   заявление метода и что обязано содержать его описание, чтобы другой
   человек выполнил метод без автора.
2. Примени эти обязательства к моему методу: составь method claim
   (participant meanings, applicability, conditions, intended effect,
   bounds, ближайшая остановка) и перечень необходимых MethodDescription.
3. Не выдумывай факты проекта; где не хватает сведений — явный пробел.
   Не выдавай выбор паттерна за выбор предметного метода.
Пиши ответ в файл.
```

Механика через MCP: `query_fpf_spec` в режиме `proof`, два запроса — по одному на паттерн.

**Проверка ответа:** тест передачи — отдать описание человеку вне контекста; если у него вопросы «а что значит…» — описание не готово, это пробел, а не его тупость.

## Шаг 06 — P2W-развёртка (12 позиций)

**Шаблон:**

```
Проект: [название]. Принятая проблема: [шаг 01]. Выбранный метод: [шаг 05].
Построй P2W-развёртку из 12 позиций (проблема → критерий → кандидаты →
пригодный метод → приспособленный метод → план → готовность → выполнение
работы → участие в преобразовании → измеритель → до/после → решение).
Карта выражает зависимость результатов, а не очередь работ (мантра ≠ план).
Для каждой позиции: содержание применительно к моему проекту и честный
статус (✅ / ◐ / 🔴 / ❌ / ⏳) с одним основанием фактуры, не пожеланием.
Назови САМЫЙ РАННИЙ переход без обоснованного результата — это место входа
(а не последний заметный симптом). Предложи паттерн для результата
СЛЕДУЮЩЕГО перехода от места входа. Пиши ответ в файл.
```

**Проверка ответа:** статусы по фактуре («исполнитель = пилот вручную» → 🔴), а не по желаемому. Если всё ✅ — агент угодничает.

## Шаг 07 — Потоки применения и создания (E.18, A.12)

**Шаблон (форма семинара 3, таблица позиций):**

```
Целевая система: [из шага 02]. Выбранная структура: [из шага 04/05].
Найди и примени E.18 (Transformation Flow Structure):
1. Поток применения: от [стартовое событие] до [полезное изменение в мире] —
   таблица из 3-5 существенных позиций (вход / выход / допустимое
   преобразование по A.3.4), покажи ветвление/соединение.
2. Поток создания/изменения системы (build the builder): от [требование]
   до [система уточнена].
3. По A.12 (Acting-Side Externalization) покажи связь: где система из потока
   создания получает роль преобразователя в потоке применения.
4. Для одной намеченной работы назови готовое и недостающее.
Не календарный план — отношение создания и использования. Пиши ответ в файл.
```

**Проверка ответа:** поток применения замыкается на изменение в физическом мире (у нас: вмешательство на ферме), а не на «отчёт сформирован».

## Шаг 08 — Проверка языка (C.2.P / E.10)

**Шаблон (дословная форма практики 4 семинара 4):**

```
Вот точная фраза: [фраза].
Вот её исходный контекст или ссылка: [абзац, таблица или ссылка].
Следующая работа: [назвать]. Нужный результат этой работы или вывод
из фразы: [назвать].
Сначала проверь границу по явному правилу: применяй E.10 (Unified Lexical
Rules for FPF), только если фрагмент намеренно использует FPF-термины или
идентификаторы либо заявляет соответствие FPF; иначе применяй C.2.P
(Epistemic Precision Restoration) и при необходимости заимствуй тесты E.10.
Объясни выбор режима одной строкой.
Дай обычный предполагаемый смысл; восстанови интересующую сущность,
утверждение, возможные типы (kinds) и отношения; найди и примени подходящий
предметный паттерн FPF; предложи одну понятную точную формулировку,
укажи, для какого вывода она даёт основание и какой более сильный вывод
не обоснован. Если предметное решение ещё не принято, не маскируй это
редактурой. Пиши ответ в файл.
```

**Проверка ответа:** ищем точно названный предмет и работу, которую теперь можно выполнить без угадывания, — а не число найденных «нарушений». Если итог похож на схему данных — дополнительно просим F.19 («объясни обычной инженерной фразой»).

## Дословные запросы остальных практик семинара 4

### Предмет и утверждение одной фразы (практика 1, C.2.1 + E.10.D2)

```
Найди и примени C.2.1 (U.Episteme: Constitution, Empirical Grounding, and
Edition Relations) и E.10.D2 (EntityOfConcern, Description Episteme, and
Specification-Use Discipline). В этой фразе: [фраза или ссылка] помоги
обычным русским языком установить, о какой интересующей сущности говорится
и что именно о ней утверждается. Затем предложи возможный тип (kind) этого
предмета в FPF, назови действующую схему обозначения или недостающий способ
интерпретации и следующую работу, для которой нужна эта точность.
Не исправляй весь документ. Пиши ответ в файл.
```

Если агент переписывает стиль, не восстановив предмет — велеть начинать с двух вопросов: «о чём?» и «что утверждается?».

### Два варианта для двух читателей (практика 2, C.2.1 + E.17 + E.24.PUB)

```
Вот фрагмент или ссылка: [текст]. Найди и примени C.2.1, E.17 (Multi-View
Publication Kit) и E.24.PUB (Ontic Description and Publication Discipline).
Подготовь два коротких варианта для [читатель и работа] и [другой читатель
и работа]. Сначала назови исходные утверждения и интересующую сущность.
Затем подготовь проверку: могут ли оба варианта быть двумя публикационными
формами одной редакции без изменения утверждений или адаптация создаёт
отдельную эпистему? Для каждого варианта объясни выбор языка, уровня
подробности и формы, перечисли опущенные различия и укажи, при какой задаче
читателю понадобится исходная редакция. Пиши ответ в файл.
```

Критерий брака: агент сделал «короткую и длинную версии», не назвав различие читательских работ и потерянные различия.

### Ранняя зацепка (практика 3, A.16.1)

```
Вот исходный материал: [одна фраза или ссылка]. Найди и примени A.16.1
(U.PreArticulationCuePack). Сначала различи сырой сигнал или иной источник,
наблюдаемый симптом, выбранную раннюю зацепку и возможные догадки. Сохрани
ядро зацепки, причину сохранения, главного свидетеля или опору и две-три
возможные ветви разбора, если они уже видны. Не выбирай маршрут, не ставь
диагноз и не придумывай обоснование. Скажи, какое новое различение
потребуется, чтобы позже применить B.4.1 (Observe → Notice → Stabilize →
Route) либо перейти к проверяемому утверждению. Пиши ответ в файл.
```

Полезен ответ, который удерживает различие «источник / симптом / зацепка / догадки», а не тот, что звучит окончательно.

### Карточка спорного имени (практика 5, F.18)

```
Термин [термин] употреблён в этих одной-двух фразах [фразы]; дальше им
будут пользоваться [читатели] для [названная работа]. Примени F.18
(Local-First Unification Naming Protocol). Сначала восстанови именуемое
значение, его тип (kind) и предметный паттерн; если данных недостаточно —
задай вопрос. Подготовь проверку, нужна ли карточка имени (NameCard) или
достаточно локальной фразы. Для устойчивого имени построй минимальный набор
кандидатов, покрывающий подходящие смысловые семьи и соседние предметы.
Сравни по семантической верности, удобству читателя, удобству образования
словоформ и риску ложных ассоциаций. Предложи техническое (TechLabel) и
обычное (PlainLabel) имена, назови существенные отклонённые варианты и
подготовь карточку имени, не выдумывая отсутствующие основания выбора.
Пиши ответ в файл.
```

Полезный результат может быть отрицательным: обнаружение двух разных значений, которым нужны разные имена.

### Контролируемое огрубление (практика 6, A.6.3.CSC)

```
Вот содержательная запись: [текст или ссылка]. Для читателя [кто читает],
следующей работы [какая работа] и нужного в ней результата [какой результат]
найди и примени A.6.3.CSC (Controlled Semantic Coarsening). Сначала
восстанови точную исходную эпистему X, построй точную огрублённую эпистему
Y о том же предмете и запиши конструкцию c : X → Y со связью схем
интерпретации, сохранёнными утверждениями и запретом усиления. Заполни
шесть строк: содержательная сторона (Source-bearing side), короткая форма
(Coarsened rendering), более узкое использование (Narrower admissible use),
потеря по сравнению с источником (Source-loss mode), более сильное
неподдерживаемое использование (Non-admissible downstream use), условие
возврата (Reopen trigger). Затем дай короткую фразу для читателя.
Пиши ответ в файл.
```

Критерий брака: получился просто краткий пересказ, а область использования короткой формы не сузилась — это ещё не контролируемое огрубление.

### Разбор нормативной фразы по L/A/D/E (практика 7, A.6 + A.6.B)

```
Разбери эту фразу: [фраза и одна-две соседние фразы или ссылка]. Найди и
примени A.6 (Signature Stack & Boundary Discipline) и A.6.B (Boundary Norm
Square (Laws / Admissibility / Deontics / Work-Effects)). Сначала скажи
обычными словами, какое решение о дальнейшей работе фраза помогает принять.
Затем выдели только действительно присутствующие атомарные утверждения и
классифицируй их как определения (L), условия допуска (A), обязанности (D)
или наблюдаемые эффекты (E). Для каждого найди подходящий предметный паттерн
```
