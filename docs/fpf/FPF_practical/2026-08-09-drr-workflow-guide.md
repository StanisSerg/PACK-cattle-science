# Шпаргалка: DRR — запись обоснования решения

> Источник: FPF E.9 (DRR Method), E.9.DA (оценка), E.23 (петля улучшения). Разбор сессии 09.08.

## Что такое DRR

Запись обоснования **одного ограниченного решения**, сделанная **до** реализации. Не протокол, не план, не документация после факта — а «почему выбрали так».

**Ядро — 4 вопроса:**

1. **Problem frame** — о чём решение, почему сейчас
2. **Decision** — выбранный ответ (позитивно) + что меняется + первое действие + ближайшая граница
3. **Rationale** — почему этот ответ (только альтернативы, объясняющие выбор)
4. **Consequences** — что следует, цена, условие переоткрытия (reopen)

**Ключевое различие:** DRR *записывает* решение, но не *принимает*, не *авторизует*, не *исполняет*. Заполненный DRR ≠ решение принято. Принятие — отдельный акт человека.

**Когда НЕ нужен:** опечатки/мелочи → лёгкий вариант CC-DRR.5 (контекст + «семантика не меняется»). Применение уже принятого паттерна → вообще без DRR.

## Полный цикл

```
0. ТРИГГЕР → 1. ЗАПИСЬ → 2. ОЦЕНКА → 3. ПРИНЯТИЕ → 4. РЕАЛИЗАЦИЯ → 5. ЗАКРЫТИЕ → 6. ЖИЗНЬ
             E.9        E.9.DA      человек       содержание →    DRR =          reopen →
             (писатель)  (ревьюер)   (владелец)    Pack/Core      провенанс      successor DRR
                          │↑
                       2а. E.23 (починка → снова на E.9.DA)
```

0. **Триггер** — решение, где важно «почему». Мелочь — cheap stop.
1. **Запись (E.9)** — 4 компонента обычным точным языком. Статус draft.
2. **Оценка (E.9.DA)** — ревьюер с чистым контекстом, рубрика из 15 координат (шкала 0–5). Статусы:
   - `admissibleForDeclaredAuthoringUse` — можно дальше
   - `repairBeforeDrafting` — есть провалы → 2а
   - `newFrameRequired` — не тот вопрос → E.22
   - `splitDecisionRequired` — склеены несколько решений → разделить
   - `holdForArchitectureDecision` — сначала архитектурное решение
2а. **Починка (E.23)** — правка → **возврат на E.9.DA** (не вперёд!). Петля крутится до admissible. «16 вариантов» Левенчука = 16 оборотов петли.
3. **Принятие** — admissible ≠ принято. Решает владелец (человек).
4. **Реализация** — содержание уходит в выбранные локусы. Можно уточнять примеры/формулировки; нельзя менять ответ, локусы, границы (иначе — successor DRR).
5. **Закрытие** — DRR остаётся как провенанс («откуда взялось»), не как второй дом содержания.
6. **Жизнь** — reopen-условие сработало → старый DRR НЕ правится; пишется successor DRR со ссылкой на прежний.

## Мнемоника петли

E.9 — написал → E.9.DA — спросил «готово?» → E.23 — «нет, вот почему» → поправил → опять спросил.

## Шкала E.9.DA (оценка записи, не идеи)

- **1–2** — решение в голове, запись — конспект для себя
- **3** — по записи может работать другой, местами догадывается
- **4** — запись самодостаточна: ответ, границы, первое действие восстановимы без автора
- **5** — редкость: на запись опираются другие решения

Статус берётся по **провалившимся координатам** (принцип пола), не по среднему баллу: одна 1 по ключевой координате = repairBeforeDrafting.

## Анти-паттерны (чем DRR не должен стать)

- **Процессный бриф** — статусы и движение бумаг вместо решения
- **Теневая спека** — содержание осталось в DRR, не дошло до Pack
- **Четырёхметка-пустышка** — заголовки есть, содержания нет
- **Кандидат без решения** — «наверное, потом посмотреть» вместо «выбрано / отклонено / вне решения»
- **Декоративный SoTA** — источники для красоты, не меняющие ответ

## Мостик к IWE

WP-файл ≈ DRR · `/verify` ≈ E.9.DA · утверждение пилота = стадия 3 · capture-процесс = стадия 6. Главное различие для практики: **решение пишется до реализации, и «проверено ревьюером» ≠ «принято мной»**.
