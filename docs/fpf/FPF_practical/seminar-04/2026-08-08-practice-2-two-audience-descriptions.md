# С4-П2 — Два варианта описания метода B для двух читателей (E.17)

> **Паттерн:** E.17 Multi-View Publication Kit — одна эпистема-источник публикуется в нескольких «лицах» для разных читателей **без изменения утверждения**. Лицо отличается точкой зрения (viewpoint) и объёмом (scope), а не содержанием. Лицо — не доказательство и не выполненная работа: оно только для ориентации и чтения.
> **Источник (эпистема):** `full-cycle/05-method-claim.md` — method claim метода B.
> **Два читателя:** помощник (исполнитель визита) и руководство хозяйства (принимает решение о внедрении).

---

## Вариант 1 — для помощника (исполнителя)

**Что изменилось в твоей работе на визите.**

Раньше: увидел, что надо сделать на ферме, — а дальше непонятно, можно ли самому. Теперь есть два простых правила.

**Правило 1. Список «можно самому».** Каждое быстрое изменение заранее отнесено к одному из двух классов:
- **«Делай сам»** — делаешь сразу, ни у кого не спрашивая.
- **«Только с подтверждением»** — сначала пишешь ведущему технологу, ждёшь «да».

Класс каждого действия определён ценой ошибки: если ошибиться дёшево — это «делай сам», если дорого — «с подтверждением». Список даёт ведущий; если действия в списке нет — считай его «с подтверждением».

**Правило 2. Сообщение после визита — 3 строки, не больше 2 минут:**

```
Визит был.
Сделал сам: …
Ждёт подтверждения: …
```

Подробности (фото, цифры, объяснения) — отдельно, позже, но в тот же день.

**Чего это правило НЕ делает:** не учит, *какое* изменение правильное по сути (это твоя предметная работа), и не заменяет ответ ведущего по дорогим действиям.

---

## Вариант 2 — для руководства хозяйства

**Проблема.** Цепочка «визит помощника → информация у ведущего → изменения на ферме» замыкается слишком поздно: то, что нужно сделать в день визита, в день визита не делается.

**Метод.** Два связанных правила на каждом визите:

1. **Гранулированный допуск.** Все «моментные» изменения заранее разделены по цене ошибки на два класса: «помощник делает сам» и «только с подтверждением ведущего». Дешёвые ошибки делегируются исполнителю, дорогие остаются на ведущем.
2. **Лёгкий протокол сигнала.** После визита помощник отправляет сообщение по форме из трёх строк (≤2–3 минуты): визит был / что сделал сам / что ждёт подтверждения. Подробности — отдельно, в тот же день.

**Ожидаемый эффект и измерение.** Изменения класса «делай сам» выполняются в день визита без участия ведущего; изменения «с подтверждением» получают решение в тот же день. Метрики приёмки: доля визитов с выполненными в-срок изменениями; медианное время «визит → изменение».

**Что потребуется от хозяйства:**
- подтверждённый ведущим список допуска (содержимое — предметное решение, делает владелец метода);
- один инструктаж помощников (список + форма сигнала);
- окно дня, в которое ведущий доступен для подтверждений.

**Границы метода.** Не решает качество предметных решений и мотивацию помощников; не масштабируется на >2–3 хозяйств без бота-формы. **Условие остановки:** если через 4–6 недель пилота доля своевременных изменений не растёт — диагностика (список / выполнение / причинная гипотеза), а не автоматическое «усиление».

## Проверка по E.17 (дисциплина публикации)

| Проверка | Результат |
|---|---|
| Оба варианта — об **одном** методе (одна забота, один способ) | ✅ источник един: `05-method-claim.md` |
| Различия — только viewpoint и scope, не содержание | ✅ помощнику — «что делать», руководству — «зачем, эффект, цена, границы»; утверждения те же |
| Нет новых обязательств, которых нет в источнике | ✅ допуск, форма сигнала, метрики, границы, остановка — все из method claim |
| Лицо не выдаёт себя за выполнение/доказательство | ✅ запись о выполнении (сигнал помощника) — отдельный факт, не часть описания |
| Противоречия между лицами | ✅ не обнаружены (противоречие = дефект редакции, не «другой метод») |

**Форма публикации:** ordinary (лёгкая) — оба лица для ориентации и чтения, без внешних обязательств; полная запись MVPK не требуется (по stop condition E.17).
