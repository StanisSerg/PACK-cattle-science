## Привязка к FPF — обязательная, локальная процедура

При работе с файлами в следующих директориях агент **ДОЛЖЕН** привязать артефакт к паттернам FPF **до** начала создания или редактирования:

- `DS-cattle-cases/cases/` — сырые кейсы (внешний репо)
- `pack/rules/` — правила Pack
- `pack/cattle-science/01-domain-contract/` — границы и различения
- `pack/cattle-science/03-methods/` — методы оценки

Источник истины — локальная спека `../library/FPF/FPF-Spec.md` (актуальность держится weekly fetch + проверкой в «начинаем работу»). MCP `fpf_reference` в контуре не развёрнут (решение пилота 30.09) — работаем напрямую по файлу спеки.

### Алгоритм

1. Определить тип задачи → взять ожидаемые паттерны из таблицы ниже.
2. Проверить каждый ID по спеке счётом **plain substring**: `grep -c -F "A.15" ../library/FPF/FPF-Spec.md` (не word-boundary regex — ID с точечными суффиксами дают ложное «отсутствует») → прочитать найденную секцию целиком. ID, не найденный в спеке, искать `grep -rn` по всему `library/FPF/` (часть ID живёт в `Engineering DPF Suite/`), прежде чем считать утраченным.
3. Тип задачи вне таблицы → метод `../library/methods/thinking/fpf` + оглавление спеки (первые ~200 строк) для навигации.

### Что фиксировать в артефакте

- `fpf_context: ["A.15", "C.11"]` — во frontmatter артефакта;
- `fpf_verified: "YYYY-MM-DD; grep FPF-Spec.md @<short-hash>"` — дата и способ проверки (hash: `git -C ../library/FPF rev-parse --short HEAD`);
- constraints из прочитанных секций — проверить перед финализацией; пробелы и неоднозначности — в раздел «Вопросы / Требует проверки».
