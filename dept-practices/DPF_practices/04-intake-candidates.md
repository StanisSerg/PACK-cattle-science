# 04 — Intake: вопрос архитектуры и кандидаты

> **Зачем этот этап (простыми словами):** Прежде чем писать, решаем, В КАКОМ ВИДЕ записать знание: одна большая инструкция «всё в одном» или две отдельные — «сначала пойми, что сломалось» и «потом чини по типу поломки». Это как решить, строить один сарай или два: переделать на середине стройки — выбросить вложенное. От выбора зависит всё дальше: сколько файлов писать, как их проверять, что унаследует отдел. Здесь варианты выложены с плюсами и минусами, а выбор делает человек — не агент. Если пропустить этот этап, начнёшь писать первый попавшийся вариант и узнаешь о его слабости ценой переписывания всего.

> Правило шага: дешёвый выход ИЛИ пригодный DRR; два архитектурных кандидата; решение принимает человек, агент записывает.

## Открытая граница (вопрос решения)

DPF «Разрывы цикла консультационного визита» — **сколько паттернов и какой гранулярности** несут переносимое знание? От ответа зависит: форма тел (E.8), приёмка холодным читателем (шаг 05), перенос на новый случай (шаг 08) и то, что унаследует LPF отдела (шаг 09).

Вход для кандидатов: 4 механизма разрыва (шаг 02: поздно / непригодная форма / без приоритета / неполное выполнение) × противоречие SoTA «полнота vs краткость» (шаг 03) × near-miss «ждали анализы кормов» (частый, нужен разделитель).

## Кандидат A — один паттерн-матрица «Разрыв цикла визита»

Одно тело E.8: типология 4 механизмов + наблюдения-признаки каждого + работа устранения + разделитель near-miss + границы.

- **Плюсы:** один вход, читается за один присест; холодный читатель видит всю картину сразу; дешевле в сопровождении (одно тело, один Refresh Route).
- **Минусы:** смешивает две работы — распознавание (диагностика) и устранение (выбор работы); матрица «4 типа × работы» раздувает Solution; при новом механизме (5-м, 6-м) правится весь паттерн.

## Кандидат B — пара паттернов «распознай → устрани»

- **P1 «Распознай разрыв цикла визита»:** наблюдения → тип разрыва (4 механизма) + явный вопрос-разделитель near-miss («изменение отложено в ожидании данных?»). Результат — тип разрыва или «цикл цел».
- **P2 «Замкни цикл визита»:** по типу разрыва — работа: допуск по цене ошибки (время/полномочия — здесь живёт метод B), эскалационное кадрирование SBAR-подобное (приоритет), read-back + форма носителя (форма), чек-лист полноты визита (полнота, с оговоркой Онтарио: внедрение важнее формы).

- **Плюсы:** честное разделение работ (диагностика ≠ лечение); P1 применим сам по себе (дешёвая диагностика на любом визите); новые механизмы добавляются в P1, новые работы — в P2; near-miss живёт в P1 как граница.
- **Минусы:** два тела вместо одного; холодному читателю нужен вход через пакет (README), а не через один файл; риск разъезжания типологии (P1) и работ (P2) при правках.

## Кандидат C — дешёвый выход: только LPF, без DPF

Записать всё как местную практику отдела (метод B + дополнения под случаи 2–4) без переносимого ядра.

- **Вердикт по гейту (00):** отклонён — трудность повторяется по хозяйствам, различения переносимы; но оставлен как сравнительный базис «а что если без DPF».

## Сравнение (A.19.ECS)

| Характеристика | A: один паттерн | B: пара | C: только LPF |
|---|---|---|---|
| Покрытие 4 механизмов | да | да | частично (метод B — только 2) |
| Честность работ (диагностика ≠ устранение) | нет | **да** | нет |
| Вход холодного читателя | **проще** | через README пакета | н/д |
| Защита от near-miss | внутри матрицы | **явным разделителем в P1** | нет |
| Цена добавления 5-го механизма | правка всего тела | точечная | — |
| Переносимость на новое хозяйство | да | **да + диагностика отдельно** | **нет** |
| Нагрузка сопровождения | **ниже** | выше (2 тела) | низкая |

## Рекомендация агента

**Кандидат B.** Решающий аргумент: случаи 3–4 показали, что ошибка практики — не «не знал работу», а «не распознал тип разрыва» (сообщил вскользь / пропустил шаги). Отдельный P1 делает распознавание самостоятельным проверяемым результатом; SoTA-линия 2 (эскалация ≠ handoff) подтверждает: разные разрывы требуют разных форм, и сначала надо знать, какой разрыв.
