# VISIT-CYCLE-LOCAL-PRACTICE · LPF отдела · Цикл визита (местная практика)

> **Зачем этот этап (простыми словами):** Общий метод (DPF) говорит «что делать вообще», но не отвечает на бытовые вопросы вашего отдела: в каком чате писать, до которого часа ждать ответ ведущего, что конкретно помощнику можно делать самому на ваших фермах, какие пункты в чек-листе аудита. Этот файл — перевод общего метода на местный язык: роли поимённо, формы сообщений, пороги «что существенно», цифры, по которым через месяц видно, работает или нет. Если пропустить этот этап, паттерн останется красивой теорией в папке: помощник не узнает, что именно от него изменилось в понедельник. Метки **[П]** — места, где решение может принять только пилот: он знает свои хозяйства и людей.

> Один DPF — много LPF. Здесь — воспроизводимая местная практика: роли, формы, окна, данные, проверка, остановка.
> Из DPF берём типологию (P1) и типы работ (P2) по значению; всё конкретное — местное.
> Перестроено по сверке 23.08 (решение пилота): одно полное тело E.8 (12 разделов) + местная мантра + компактный пакет (сем.5 пр.9 сл.97). Более узкий контекст не превращает LPF в список инструкций (сл.12): источники, читательский вход, проверка и условия обновления сохранены.

## Problem frame

Применяй, когда нужно выполнить местную работу цикла визита в этом отделе: сигнал после визита, эскалация, доклад по аудиту, подтверждение действия помощника. Читатель: помощник (новый — без автора), ведущий технолог. Не применяй как замену диагностики: тип разрыва сначала называется по P1 (DPF), этот LPF задаёт только местные формы, окна и допуски.

## Problem

DPF «Разрывы цикла визита» переносим, но намеренно не называет: канал связи, окна ответа, состав допуска помощника, пункты чек-листа, порог «существенно» и цифры приёмки. Без местного слоя каждый помощник заполняет эти пробелы по-своему: та же типология порождает несовместимые практики на разных хозяйствах, а проверить «работает ли» невозможно — не названы измеримые границы.

## Forces

| Сила | Напряжение |
|---|---|
| Конкретность vs переносимость | Местные назначения (роли, инструменты, окна) нужны для исполнения ↔ не должны протечь в переносимый DPF (→ разделение: типология и типы работ — в P1/P2 по значению; здесь только местное) |
| Полнота регламента vs рабочая краткость | Полные формы надёжнее ↔ помощник в поле работает по мантре и карточке ≤2–3 мин (→ мантра + короткие формы D2/3 строки) |
| Контроль vs доверие | Read-back и дублирование ловят сбои ↔ на рутине порождают шум и alert fatigue (→ read-back только для класса «с подтверждением») |
| Стабильность конфигурации vs калибровка | Пороги должны быть предсказуемы ↔ стартовые пороги назначены не на данных (→ явная процедура калибровки через 4 недели, § Consequences) |

## Solution

### Роли и среда

| Роль | Кто | Инструмент |
|---|---|---|
| Ведущий технолог | пилот | Telegram, этот репо |
| Помощники | 2 чел. | Telegram |
| Персонал ферм | по хозяйствам | устные указания помощника в рамках допуска |

Канал: Telegram (общий чат + ❗-эскалации). Данные о ходе работы: сообщения-сигналы, чек-листы, таблица замеров.

### Местные формы по типам разрыва (наследие P2)

**T1 · Допуск и сигнал (метод B):**
- D1 — список допуска «делай сам / с подтверждением» по цене ошибки: **[П] содержимое — пилот** (знает хозяйства).
- D2 — карточка сигнала (≤2–3 мин): «визит был / сделал сам: … / ждёт подтверждения: …» — кандидат, утвердить **[П]**.
- D3 — правило подтверждений: окно ответа ведущего **[П: какой час?]**, при тишине — **[П: безопасный вариант / повторный сигнал?]**.
- Пороги способностей помощников: полный допуск сразу или поэтапно **[П]**.

**T2 · Форма носителя:**
- Рабочая форма — короткий структурированный текст; голосовые >3 мин и сырые транскрипты — не рабочая форма (только через восстановление картины).
- Read-back обязателен для действий из класса «с подтверждением»; на рутине запрещён.
- Норма: визит «done» = данные внесены, не «написал в чат» (CS.METHOD.008).

**T3 · Эскалация:**
- Форма 3 строки: «Что случилось / чем грозит / что предлагаю до <срок>» — отдельным сообщением с ❗, не в хвосте отчёта.
- Окно приёма эскалации ведущим **[П: окно?]**; тишина за окном → повтор + звонок.
- Порог «существенно» — стартовая версия: риск здоровью коровы, падение молока >X кг/день **[П: X]**, сбой кормления; калибровка на данных через 4 недели.

**T4 · Чек-лист полноты визита** (наследует CS.METHOD.006):
- Состав пунктов под аудит кормления **[П: совместно дописать по CS.METHOD.006]**: остатки стола взвешены/внесены, пробы отобраны/промаркированы, траншея осмотрена, температура силоса измерена, THI зафиксирован (не «жара» ссылкой).
- **Правило вывода:** без закрытого чек-листа доклад = «данных недостаточно». «В норме» — только при полном чек-листе.

### Проверка и внедрение (Онтарио-предупреждение)

- Обучение: одна встреча-инструктаж + **5–9 повторений** на реальных визитах; первые 2 недели — ежедневная сверка формы сигналов.
- Контроль использования: ведущий спрашивает по чек-листам каждую неделю (ритм «сержанта»); не пользуются — разбор, не угроза.
- Проверка LPF целиком: через 4–6 недель пилота метода B — характеристики из Consequences против базовой линии **[П: замер базовой линии — вход из WP-111]**.
- **Автоматизация исполнения — только после нескольких понятных ручных проходов** и отдельного безопасного теста (сем.5 пр.9 сл.97).

### Условия остановки и восстановления

- **Остановка (honest stop, метод B):** 4–6 недель без роста доли своевременных изменений → диагностика: метод / выполнение / причинная гипотеза. Не «усиливать» автоматически.
- **Восстановление конфигурации:** текущая форма каждого артефакта (D1–D3, чек-листы, пороги) живёт в `dept-practices/`; версия и дата на каждом; откат — к прошлой редакции файла.
- **Обращение к человеку:** любой случай «предметная эскалация» из P1 (ожидание данных > предметного окна) — немедленно к ведущему, не по чек-листу.

### Местная мантра (из Solution)

> «Сигнал сразу, подробности до конца дня; "в норме" — только с полным чек-листом; существенное — с ❗, не в хвосте».

Мантра сохраняет рабочее различение (доставка vs полнота vs приоритет) и условие остановки («данных недостаточно» вместо «в норме»), а не заменяет способ лозунгом (пр.9).

## Archetypal Grounding

- **Показательный случай (применение):** визит в жару (T4, см. `08-new-case-application.md`): помощник закрывает чек-лист полноты (остатки, пробы, траншея, температура силоса, THI числом) → доклад «в норме» допустим; ведущий сверяет чек-лист в недельном ритме.
- **Показательный случай (эскалация):** помощник узнал о существенном изменении рациона → отдельное ❗-сообщение в 3 строки в тот же день, не в хвосте рутинного отчёта; тишина за окном **[П]** → повтор + звонок.
- **Случай, где LPF не выбирать:** задержка в ожидании предметных данных (анализы кормов, лаборатория) — цикл цел (near-miss NM-1 из `02-cases.md`); работа по LPF не назначается, случай уходит ведущему как предметная эскалация.

## Bias-Annotation

- **«LPF = список инструкций»:** узкий контекст провоцирует свести файл к командам; потерянные различения (границы применимости, условия остановки) восстанавливаются через Conformance Checklist и Anti-Patterns.
- **Формализм внедрения (Онтарио):** комплаентность формы принимается за эффект — поэтому приёмка по характеристикам результата (Consequences), а не по заполненности форм.
- **Персонализация:** «помощник невнимателен» вместо диагностики звена — тип разрыва называется по P1 до любых местных выводов.

## Conformance Checklist

Применение соответствует LPF, если:
1. Тип разрыва назван по P1 до выбора местной формы (LPF не заменяет диагностику).
2. Сигнал отправлен сразу, подробности — до конца дня (форма D2).
3. Эскалация — отдельным ❗-сообщением в 3 строки, не в хвосте отчёта.
4. Read-back выполнен для класса «с подтверждением» и только для него.
5. «В норме» заявлено только при полном чек-листе; иначе доклад = «данных недостаточно».
6. Предел местного правила понятен исполнителю: предметная эскалация уходит ведущему, а не в чек-лист.

## Common Anti-Patterns

| Анти-паттерн | Почему ломается | Ремонт |
|---|---|---|
| Эскалация в хвосте рутинного отчёта | Приоритет теряется (разрыв T3 воспроизводится) | Отдельное ❗-сообщение, форма 3 строки |
| «В норме» без полного чек-листа | Доклад без данных принимается за результат | Правило вывода: «данных недостаточно» |
| Read-back на рутине | Шум, alert fatigue, ненависть к форме | Read-back только «с подтверждением» |
| Автоматизация до ручных проходов | Непонятный автомат закрепляет непроверенную практику | Сначала несколько ручных проходов + безопасный тест (пр.9) |
| Правка порогов «с потолка» | Порог эскалации перестаёт отражать данные | Калибровка через 4 недели на замерах |

## Consequences

**Плюсы:** помощник действует без автора; ведущий видит сбой по цифрам, а не по ощущению; переносимый DPF не загрязнён местными назначениями. **Минусы:** стартовые пороги — экспертные, не откалиброваны; поддержка двух слоёв (DPF + LPF) требует дисциплины редакций; конфигурация привязана к Telegram.

**Несводимые характеристики (3–5) с нижними границами:**

| Характеристика | Нижняя граница | Свидетельство |
|---|---|---|
| Доля визитов с изменениями в день визита | ≥ [П: старт 50%?] → рост за 4–6 недель | таблица визитов |
| Медианное время «визит → изменение» | ≤ 1 день | метки сигналов |
| Эскалации с ответом в окне | 100% (иначе окно нереально) | ❗-сообщения |
| Визиты с полным чек-листом | ≥ 90% через месяц внедрения | чек-листы |
| Докладов «в норме» без полноты | **0** | выборочная сверка ведущим |

## Rationale

Местные формы наследуют типологию P1 и типы работ P2 **по значению**, а не копированием — иначе правка типологии породила бы рассинхрон. Допуск по цене ошибки (D1) — из метода B: ошибка «сделал сам» дороже ошибки «подождал подтверждения» только для части действий. Окно ответа + read-back — баланс Forces «контроль vs доверие». Калибровка порога эскалации через 4 недели — потому что порог, назначенный без данных, либо топит ведущего в шуме, либо прячет критичное (SoTA линия 3, MBE).
