# DRR: Архитектура DPF «Разрывы цикла визита» — пара паттернов

## Проблема

DPF строится на корпусе из 4 случаев с четырьмя разными механизмами разрыва цикла визита (поздно / непригодная форма / без приоритета / неполное выполнение). Нужно решить, в скольких паттернах и какой гранулярности записывать переносимое знание, чтобы: новый случай диагностировался без автора, near-miss («ждали анализы кормов») отсекался, а LPF отдела получал понятное наследство. Решение нужно до написания тел паттернов: от гранулярности зависит форма шагов 05–08.

## Решение

**DPF = пара паттернов: P1 «Распознай разрыв цикла визита» + P2 «Замкни цикл визита».**

- **P1 (диагностика):** вход — наблюдения за циклом визита; выход — один из 4 типов разрыва или «цикл цел». Содержит явный вопрос-разделитель near-miss: «изменение отложено в ожидании данных? — цикл цел, паттерн неприменим».
- **P2 (работа):** вход — тип разрыва из P1; выход — работа под тип: допуск по цене ошибки (разрыв по времени; «полномочия» здесь — аспект типа «время», не пятый тип: кому позволено действовать в день визита; сюда входит метод B), эскалационное кадрирование (приоритет), read-back + форма носителя (форма), чек-лист полноты визита (полнота; с оговоркой: внедрение важнее формы — Онтарио). Разрешение противоречия SoTA «полнота vs краткость»: форма сообщения выбирается типом разрыва, а не единым стандартом — эскалация короткая (SBAR-подобная), передача деталей полная.
- Связь: P2 обязан ссылаться на типы P1 по значению; противоречие типологий — дефект редакции.

**Чего НЕ делаем:** не пишем один паттерн-матрицу (кандидат A отклонён); не сливаем всё в LPF (кандидат C отклонён гейтом 00); LPF-обвязку (список D1, формы, окна) в DPF не поднимаем — она шаг 09.

**Первое действие:** написать Solution P1 — типология 4 разрывов с наблюдениями-признаками и near-miss-разделителем; приёмка холодным читателем (шаг 05).

**Переоткрываем, если:** появится 5-й механизм, не ложащийся в типологию P1 (тогда — successor DRR о расширении); или P1/P2 начнут дублировать друг друга при правках (тогда — слияние в один паттерн, т.е. возврат к кандидату A).

## Почему так

- **Случаи 3–4 — ошибки распознавания, а не незнания работы:** помощник «сообщил вскользь» и «пропустил шаги» — в обоих работа была известна, не был распознан тип ситуации. Отдельный P1 делает распознавание самостоятельным проверяемым результатом.
- **SoTA, линия 2:** эскалация ≠ handoff (SBAR vs I-PASS) — разные разрывы требуют разных форм сообщения; сначала надо знать тип. Подтверждает разделение.
- **Против A:** матрица «4 типа × работы» в одном Solution смешивает диагностику и лечение; добавление 5-го механизма правит всё тело; near-miss тонет в матрице вместо явной границы.
- **Против C:** гейт 00 — трудность повторяется по хозяйствам, различения переносимы; только-LPF оставляет каждое новое хозяйство без ядра.
- **Цена B:** два тела вместо одного; риск разъезжания типологии (P1) и работ (P2) — смягчается правилом «P2 ссылается на типы P1 по значению» + переоткрытием при дублировании.

**Маркер опоры:** тезис «случаи 3–4 — ошибки распознавания» — со слов пилота; для случая 4 («пропустил шаги аудита») аргумент слаб — это может быть и незнание чек-листа. Выбор B держится на остальных аргументах и без него.

**Диспозиция неиспользованного из SoTA (что сознательно не вошло):**
- **Линия 1 (HHPM: письменный отчёт как обязательный элемент; «точка done = внесение в систему»; CS.METHOD.006/008):** принимается частично — чек-лист полноты визита в P2 наследует CS.METHOD.006 (сбор → верификация → WorkPlan), разграничение: P2 называет работу и её тип, CS.METHOD.006 остаётся действующим методом отдела; при написании тела P2 проверить функциональное дублирование (триггер переоткрытия). «Точка done = внесение» — принята как норма для P2 (форма носителя).
- **Линия 3 (менеджмент):** калибровка порога эскалации на данных — отложена в шаг 09 (LPF: пороги и окна — местные, калибруются на данных отдела); Situational Leadership — отклонена (эмпирика слабая, случай внешнего консультанта не покрыт).
- **Противоречие 3 (фильтрация vs дублирование):** разрешено — read-back обязателен только для эскалаций (дорогих), рутинные сигналы без read-back; иначе шум съест внимание ведущего.

## Что следует

- **Плюс:** P1 применим сам по себе (дешёвая диагностика на любом визите, даже без P2); LPF отдела наследует чёткую границу: типология — из DPF, списки и формы — местные.
- **Минус:** холодному читателю нужен вход через README пакета (шаг 07), а не один файл; сопровождение двух тел дороже одного.
- **Проверка решения:** перенос на новый случай (шаг 08) — если по P1 новый визит диагностируется без автора, архитектура подтверждена.
- **Зафиксировано сейчас:** пара паттернов, граница P1/P2, место near-miss. Можно уточнять без переоткрытия: формулировки типов, имена паттернов, примеры.
