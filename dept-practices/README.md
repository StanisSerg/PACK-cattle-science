# LPF технологического отдела

> **LPF (Local Practice Framework)** — локальные практики отдела: как мы работаем, записанные так,
> чтобы новый технолог мог прочитать и выполнять работу без автора рядом.
> Нижний этаж лестницы: **FPF** (универсальные принципы) → **DPF ≈ PACK-cattle-science** (предметная
> область «коровники», для всех) → **эта папка** (наши хозяйства, наши люди, наши редакции).

## Как читать эту папку

1. **Сначала — верхняя карта:** `dept-system-mantra.md`. Что отдел производит для клиента и как это устроено. Одна страница, обновляется редко.
2. **Потом — реестр ветвей:** `dept-branch-registry.md`. Какие улучшения идут, какая ветвь активна, где в ней разрыв. Главный рабочий файл отдела. Ветви нумеруются стабильными ID `B-NN`, папка ветви — `branches/B-NN-slug/`; ID и папка не меняются при смене статуса. Документы внутри ветви — `B-NN.D-MM-slug.md` (порядковый номер в ветви, дата — во frontmatter); индекс документов — `README.md` в папке ветви.
3. **Дальше — по темам:** `methods/` — описания методов (по FPF A.3.2): каждое описание пишется так, чтобы исполнитель выполнил метод без автора: предусловия, параметры, семантика отказа, пороги способностей, редакция.

## Куда что кладём (WP-114, 2026-08-23)

| Что появилось | Куда | Когда уходит оттуда |
|---|---|---|
| Сырьё с площадок (docx/pdf/фото/заметки «на разбор») | `inbox/` | Разбор → материал в ветвь `branches/B-NN/` (или «не наше» → удаление). **inbox — не архив:** файлы старше 7 дней флагируются на Day Open |
| Сформулированная проблема отдела | `problems/YYYY-MM-DD-slug.md` — карточка по 5 полям (C.22.2) | После шага 4 цикла: дешёвый выход → закрыта; иначе → становится ветвью `B-NN` |
| Рабочие продукты улучшения | `branches/B-NN-slug/` | Живут в ветви по её жизненному циклу |
| Описания методов | `methods/` | Постоянный дом |

**Корень папки — только карты и реестры** (README, мантра, реестр ветвей). Рабочих файлов в корне быть не должно.

## Как заводим проблему (маршрут)

Пилот формулирует проблему («проблема: …») → агент запускает скилл **`/dept-problem`**, который автоматически:
1. Создаёт карточку проблемы по 5 полям (C.22.2) в `problems/` — недостающее спрашивает, не додумывает.
2. Прогоняет гейт дешёвых выходов (`DPF_practices/00-need-gate.md`): применить готовое / один разовый ответ / честная остановка.
3. Ведёт по ступеням полного цикла 0–10 (гайд `../docs/fpf/FPF_practical/2026-08-09-fpf-full-cycle-steps-guide.md`) с остановками на решения пилота.

Помнить маршрут не нужно — он вшит в скилл.

## Принципы наполнения (дисциплина FPF)

- **Метод ≠ описание ≠ запуск ≠ назначение** (A.3.1): метод — способ действия; описания — документы в `methods/` с редакциями; конкретный визит — работа; «кто делает» — назначение роли. Не смешивать.
- **Заимствование из DPF:** предметные методики (сита, модель кормления, жвачка) не переписываем — ссылаемся на `PACK-cattle-science` (`docs/`). Кейсы — в `DS-cattle-cases`. Здесь — только «как это делаем мы».
- **Честные пробелы:** чего нет — помечается `[ПРОБЕЛ]`, не додумывается.
- **Проверка качества:** новый технолог читает тему и выполняет работу; где споткнулся — там пробел в описании.
