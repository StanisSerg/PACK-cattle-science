# B-01.D-06: Карточка проблемы — метод внесения данных замера

## Исходная формулировка (дословно)

> «Метод внесения данных замера (контрольного доения) в учёт» (WP-112).
> «Мы сейчас не привязываемся к Остромичам. Создаем метод для работы с хозяйствами в целом. Эта ветка отдела, а не хозяйства» (пилот, 2026-08-28).
> «Важно не технологи хозяйства, а технологи технологического отдела компании» (пилот, 2026-08-28).
> «У каждого технолога свой метод фиксации информации по результатам посещений. Требуется формализация метода и приведение всех к единому стандарту» (пилот, 2026-08-28).

## Зацепка (A.16.1, минимальный пакет)

1. **Ядро наблюдения:** единого способа фиксации результатов посещения хозяйства у отдела нет — у каждого технолога свой метод. Эталонная практика (метод B, «замер и внесение данных при посещении») существует только как ручная практика пилота (CASE-002). Самый ранний разрыв длинной развёртки — переход 4→5 «метод → приспособленный (передаваемый) метод».
2. **Почему не потерять:** пока у каждого технолога свой способ, данные посещений несопоставимы между хозяйствами и контроль отчётов не работает; а эталон живёт только в руках пилота — работа не масштабируется, цепочка рвётся на нём.
3. **Главный свидетель:** `B-01.D-03-earliest-broken-transition.md` (разбор перехода 4→5, подтверждён пилотом 01.08) + `B-01.D-04-method-claim-and-description-farm-visit.md` (эскиз method claim, draft).
4. **Контрасты:** практика пилота работает (CASE-002) ↔ у технологов отдела каждого свой способ; показатели замера и поток описаны ↔ единого стандарта фиксации нет.
5. **Намёки направлений:** формализация метода B как стандарта отдела; правило «2a — до отъезда, 2b — до конца недели»; чек-лист визита; markdown-шаблон замера; договорённость с технологами отдела; пробный визит по методу.

### Step 1 — Карточка по Thin-форме (C.22.2, ред. 2026-08-25)

**1. Сигнал/зацепка:** секция «Зацепка» выше.

**2. Предмет интереса:** способ фиксации данных замера (контрольного доения) технологом отдела по итогам посещения хозяйства. Схема отсчёта: длинная P2W-развёртка (`B-01.D-01`, позиции 4→5) и поток работ (`B-01.D-02`). Граница утверждений: внутри — фиксация и внесение данных по итогам посещения (все показатели → md-таблицы кейса хозяйства — первичный приёмник; сита и СВ дублируются в АМТС для корректировки рациона — уточнение пилота 2026-08-28); вне границы — методика самого контрольного доения на ферме, расчёт рационов, план обучения технологов.

**3. Семейство утверждения:** доступность метода. Факт: метод B существует как ручная практика пилота (CASE-002, апробирован). Отсутствует: доступность метода отделу как передаваемого стандарта фиксации.

**4. Почему не пожелание, не тикет, не предвыбранная работа:**
- Не пожелание: есть наблюдаемый разрыв (разбор перехода 4→5, подтверждён пилотом 01.08) и цена — данные посещений несопоставимы между хозяйствами, контроль отчётов не работает, масштабирование упирается в пилота.
- Не тикет: нет готового исполнителя и готового способа — предмет требует формализации (заявление + описание метода, пробелы зафиксированы в `B-01.D-04`).
- Не предвыбранная работа: на ступени выбора метода честно рассматривается палитра — метод пилота как эталон / способы технологов / гибрид (правило 2–5 кандидатов).

**5. Что считать улучшением (приёмочная проба):**
- **Пилот метода:** 2 технолога-помощника + ведущий технолог (пилот) вносят данные посещений по единому шаблону: поля замера — до отъезда (2a), таблицы и оформление записи — в пятницу до 20:00 (2b); устойчивость — 4 недели подряд без возвратов на переделку.

### Фактура: текущие способы фиксации (вход пилота 2026-08-28)

1. **Записная книжка** — основной способ: технологи-помощники фиксируют данные у себя на бумаге.
2. **Telegram** — по некоторым хозяйствам, точечно: обычно pH мочи.
3. **Сводные таблицы по запросу** — продуктивность по группам, динамика реализации молока, выбытия и т.п. сводятся только при запросе ведущего технолога или хозяйства; делается долго и воспринимается технологами как дополнительная работа.
4. **Отчёты — у каждого своя форма.**
5. **Следствие:** сравнить разные хозяйства невозможно из-за разности вида отчётов.

**Наблюдение для ступени выбора метода и внедрения (не отвергать молча):**
- Палитра кандидатов: **A** — метод B пилота (2a/2b, АМТС + markdown-архив, CASE-002); **B** — книжка + точечный Telegram (текущее); **C** — сводные таблицы по запросу (текущее); возможен **гибрид**. B и C — не кандидаты в стандарт (они и есть проблема), но различающая проба обязана извлечь их сильные стороны: низкий порог записи в моменте (книжка всегда под рукой) и мгновенная доставка сигнала ведущему (Telegram).
- **Риск внедрения:** сведение таблиц уже воспринимается как допработа → если стандарт ощутится как «ещё одна допработа», внедрение упадёт (оговорка Онтарио: форма без внедрения не работает — SoTA-пара «чек-лист эффект/не-эффект», Urbach 2014 / Haynes 2009). Стандарт обязан **заменять** текущие формы, а не добавляться к ним, и давать технологу видимую отдачу (меньше сведений по запросу).

**Диспозиция палитры (итог ступени выбора метода, 2026-08-28):**
- **Выбран кандидат A** — метод пилота как эталон стандарта: заявление `B-01.D-07` утверждено пилотом 2026-08-28.
- Кандидаты B (книжка + Telegram) и C (таблицы по запросу) **отвергнуты** — они и есть проблема (несопоставимость).
- Гибрид — **отклонён как самостоятельный кандидат**; сильные стороны B извлечены и перенесены в выбранный метод:
  - низкий порог записи в моменте (книжка) → компенсировано тем, что md-таблица — первичный приёмник в момент визита (заполняется на месте, без «сведений потом»);
  - мгновенный сигнал ведущему (Telegram) → компенсировано правилом эскалации и уведомления в день визита (D-08 п. 1.4, §4.3 — канал Telegram утверждён пилотом 2026-08-28).
